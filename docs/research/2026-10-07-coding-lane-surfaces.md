# Coding lane surfaces

Research note for ADR-0018 (coding agents are execution lanes) and ADR-0019 (worker-hosted first). Every claim below was read from an official doc, package registry or repository source on 2026-10-07; the version or commit read is in `# Citations`. Where the three providers disagree with the historical [Cursor fact sheet](../../../mission-control-general/runtime-facts/CURSOR_SDK_FACTS.md) (1.0.31), this note wins. "UNVERIFIED" marks a claim the sources did not settle.

## Summary

All three platforms can sit behind the [Harness](../../GLOSSARY.md) protocol as worker-hosted [Lanes](../../GLOSSARY.md), but with different native strength on each operation. Claude Code (Python `claude-agent-sdk` 0.2.164 driving the bundled CLI 2.1.292 over stdio) has the richest in-process control: Python hook callbacks, a `can_use_tool` decider, native session fork, a queue with an interrupt receipt, and a result stream that carries per-turn usage and a client-side cost estimate. Codex (app-server JSON-RPC, `openai-codex` Python 0.161.0) has the most explicit wire protocol: stable thread/turn/item ids, native `turn/steer` mid-turn injection, `turn/interrupt`, `thread/fork`, approval requests the client must answer, and per-turn token usage, but no cost on the wire and a `turn/start` that silently steers when a turn is active. Cursor (`cursor-sdk` Python 1.0.37 over a bridge binary) is the thinnest: no Python steer, no fork, no pause, file-based hooks only, one active run per cloud agent, and billed cost that settles later. Cloud placement is weakest on Claude (no programmatic event stream for cloud sessions found) and strongest on Cursor (REST v1 beta with resumable SSE). None of the three lets the agent write back to mission state; each emits enough identified events for a [Reducer](../../GLOSSARY.md) to derive attempt state from the accumulated transcript, with the gaps listed per provider.

## Claude Code via the Claude Agent SDK for Python

### 1. Lifecycle

A session is created by the first `query()` or `ClaudeSDKClient.connect()`; the SDK spawns the bundled `claude` CLI as a subprocess (`--input-format stream-json`, `--output-format stream-json`). The session id arrives in `SystemMessage.data["session_id"]` on the `init` message and on every `ResultMessage.session_id`. `ClaudeAgentOptions` pre-assigns it with `session_id` (must be a UUID), resumes with `resume=<id>` or `continue_conversation=True`, forks with `fork_session=True`, and truncates with `resume_session_at` / `resume_drops_turn` (SDK 0.2.137+; the CLI refuses a truncation that would drop entries not attributable to the named turn). Transcripts are JSONL at `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`, relocatable with `CLAUDE_CONFIG_DIR` and `CLAUDE_CODE_PROJECT_DIR_NAME` (SDK 0.2.140+); the entry format is declared internal and version-unstable. Since CLI 2.1.223 `resume` finds the id across projects on the same machine. Cross-host resume needs the `SessionStore` protocol (`append`, `load`, `list_sessions`, `delete`, `list_subkeys`; `session_store_flush="eager"` streams frames per message) or copying the file. Helpers: `list_sessions`, `get_session_messages`, `get_session_info`, `fork_session`, `delete_session`, `list_subagents`, `get_subagent_messages`. The session ends with `disconnect()` (stdin closed, then signals); SIGTERM exits 143 and records no result for the open turn; on resume a cut-off tool call is shown to the model as cut off (CLI 2.1.281+) unless `CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1`.

Reattach after a worker crash: the agent loop lives in the worker's subprocess, so it dies with the worker. There is no attach-to-running-process API for SDK sessions; recovery is `resume=<session_id>` into a fresh process, which the harness must report as emulated `reattach`. The TypeScript `reinitialize()` re-delivers pending permission requests after a transport gap; the Python client has no equivalent (UNVERIFIED whether `get_server_info()` serves that purpose).

### 2. Turn control

Streaming input mode (`ClaudeSDKClient.query()` while a turn runs) queues messages, which "process sequentially" at the turn boundary; the CLI may merge several queued messages into one turn. `interrupt()` aborts the current turn (`ResultMessage.terminal_reason` is `aborted_streaming` or `aborted_tools`). Where the CLI advertises `interrupt_receipt_v1` in `system/init.capabilities` (CLI 2.1.205+), the interrupt control response lists `still_queued` user-message UUIDs; `interrupt_cancel_queued_v1` (2.1.219+) lets a raw control request pass `cancel_queued: true` and lists them under `cancelled`. The receipt arrives before the interrupted turn's result. Python `interrupt()` is typed `-> None`, so the receipt is not surfaced to Python callers (UNVERIFIED whether it is parsed internally). Single-message mode (`query()` with a string) supports neither queueing nor interruption. There is no mid-turn steer primitive; cooperative injection is available only through hooks (`PostToolUse.additionalContext`, `UserPromptSubmit`). There is no pause; the closest native mechanism is a `PreToolUse` hook returning `permissionDecision: "defer"`, which ends the turn with `stop_reason: "tool_deferred"` and `ResultMessage.deferred_tool_use` (tool id, name, input), to be resumed later with the same `session_id`. Fork is native (`fork_session`, optionally at `resume_session_at`) and branches conversation only, not files; `enable_file_checkpointing` plus `rewind_files(user_message_id)` covers files. `set_permission_mode`, `set_model`, `toggle_mcp_server`, `stop_task` act mid-session.

Mapping: `send_turn` native (queue at turn boundary, `turn_boundary_guaranteed`); `cancel_turn` native with receipt; `interrupt_and_inject` emulated as `cancel_and_replace` (`interrupt()` then `query()`); `pause` emulated as `pause_at_tool_gate` (defer) or `emulated` (interrupt at a boundary); `fork` native for conversation, emulated for workspace.

### 3. Hooks and middleware

Python callback hooks (`ClaudeAgentOptions.hooks: dict[HookEvent, list[HookMatcher]]`): `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `PreCompact`, `Notification`, `SubagentStart`, `PermissionRequest`. Not available as Python callbacks (TypeScript only): `SessionStart`, `SessionEnd`, `PostCompact`, `StopFailure`, `PostToolBatch`, `Elicitation`, `ElicitationResult`, `ConfigChange`, `InstructionsLoaded`, worktree, cwd and task events; those still fire as settings-file hooks (handler kinds `command`, `http`, `mcp_tool`, `prompt`, `agent`) when the matching `setting_sources` entry is loaded. Hooks for one event run concurrently; `deny` beats `defer` beats `ask` beats `allow`; async hook outputs cannot block. Permission evaluation order: hooks, deny rules, ask rules, permission mode, allow rules, then `can_use_tool` (`CanUseTool = Callable[[tool_name, input, ToolPermissionContext], Awaitable[PermissionResultAllow | PermissionResultDeny]]`, `PermissionResultDeny(interrupt=True)` aborts the turn). A `PreToolUse` deny applies even in `bypassPermissions`; auto-approved tools never reach `can_use_tool`, so a side-effect gate belongs in `PreToolUse`. Per-session injection: `system_prompt` (string, `claude_code` preset with `append`, custom, file), `mcp_servers` with `strict_mcp_config=True`, in-process tools via `create_sdk_mcp_server` and `@tool`, `agents`, `skills`, `plugins`, `sandbox`, `permission_mode` (`default`, `acceptEdits`, `plan`, `bypassPermissions`, `dontAsk`, `auto`), `setting_sources=[]` to ignore filesystem configuration; CLI `--bare` additionally skips OAuth, hooks, skills and CLAUDE.md discovery. `include_hook_events=True` adds hook lifecycle messages to the stream.

### 4. Transcript as the source of truth

The stream union is `UserMessage | AssistantMessage | SystemMessage | ResultMessage | StreamEvent | RateLimitEvent | ConversationResetMessage`. `AssistantMessage` carries content blocks (`ToolUseBlock.id` is the stable tool-call id, matched by `tool_use_result` on the following `UserMessage` and by `tool_use_id` in hooks and `ToolPermissionContext`), `model`, `message_id`, `usage`, `stop_reason`, `parent_tool_use_id` (subagent attribution), `uuid`. `SystemMessage` subtypes include `init` (session id, model, tools, `mcp_servers`, `plugins`, `capabilities`), `api_retry`, `permission_denied`, `session_state_changed` (`running`, `idle`, `requires_action`; needs `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1`) and task progress. `ResultMessage` ends each turn with `subtype`, `duration_ms`, `duration_api_ms`, `is_error`, `num_turns`, `session_id`, `stop_reason`, `total_cost_usd`, `usage`, `result`, `structured_output`, `model_usage`, `permission_denials`, `deferred_tool_use`, `errors`, `api_error_status`, `uuid`, `terminal_reason`, `origin`. Usage: `usage` is per turn and main loop only; `total_cost_usd` and `model_usage` (per model, includes subagents, `costUSD`, `contextWindow`) are cumulative across the call and include totals restored on resume (CLI 2.1.277+); per-step `AssistantMessage.usage` dedupes by `message_id` and its `output_tokens` is a placeholder. Cost is a client-side estimate from a bundled price table, explicitly not billing. A crash emits `error_during_execution` with possibly zeroed totals.

Verdict: a reducer can derive turn state, tool calls, approvals, denials and completion deterministically from this stream without any write-back, keyed on `session_id` plus message `uuid`. Missing: authoritative cost; usage inside subagents is only in `model_usage` aggregates, not per tool call; the on-disk JSONL is not a stable contract, so the stream the worker observed (or a `SessionStore` mirror) must be the persisted record; `queued_turn_count` is documented for TypeScript results only (UNVERIFIED in Python).

### 5. Inspection

Live: `receive_messages()` (continues past results, needed for `session_state_changed`), `include_partial_messages=True` for raw API `StreamEvent`s (text and `input_json_delta`), `get_context_usage()`, `get_mcp_status()`. The transcript file is written continuously; a `SessionStore` with eager flush gives another process a near-real-time tail. After the fact: `get_session_messages`, `list_subagents`. CLI equivalent: `claude -p --output-format stream-json --verbose --include-partial-messages`, `--replay-user-messages` for input acknowledgment. No second client can attach to a running SDK subprocess (`claude attach` targets interactive background sessions; UNVERIFIED for `-p` runs).

### 6. Placement

Worker-hosted: the CLI subprocess in the worker, authenticated by `ANTHROPIC_API_KEY`, `apiKeyHelper` in `--settings`, OAuth login, or Bedrock / Vertex / Foundry credentials; `--bare` never reads OAuth. Cloud: Claude Code cloud sessions run on Anthropic VMs (or a self-hosted environment); `claude --cloud "task"` creates one from the current repository's GitHub remote, `claude -p "msg" --cloud <session_id>` queues one message into an existing session and exits (`--output-format json` returns `{ok, session_id, url}`; `stream-json` is not supported), and `claude --teleport <id>` pulls a copy of the session locally. Cloud sessions require a claude.ai sign-in (API keys are refused), the organization's `allow_remote_sessions` policy, and GitHub for clone and PR; an expired environment restores history but not background work. No programmatic observe, cancel or usage surface for cloud sessions was found (UNVERIFIED), so a Claude cloud profile today would be `send_turn` native, `observe` unsupported.

### 7. Pins

`claude-agent-sdk` 0.2.164 (PyPI, uploaded 2026-10-06T23:50 UTC; `Requires-Python >=3.10`; deps `anyio>=4`, `jsonschema>=4.20`, `mcp>=1.23,<3`); bundles Claude CLI 2.1.292. npm `@anthropic-ai/claude-code` latest 2.1.293 (read 2026-10-07). Docs pages on code.claude.com carry no dates; they describe CLI 2.1.29x behavior.

## OpenAI Codex via the app-server JSON-RPC protocol

### 1. Lifecycle

`codex app-server --listen stdio://` (default) or `ws://`, `unix://` (the ws and app-server surfaces are labelled experimental, "not supported for production workloads"). One `initialize` per connection (`clientInfo{name,title,version}`, `capabilities{experimentalApi, optOutNotificationMethods, ...}`) then `initialized`. `thread/start` returns the thread (`id` UUIDv7, `sessionId`, `path` to the rollout, model, cwd, `approvalPolicy`, `sandbox`, `instructionSources`) and subscribes the connection; `thread/resume {threadId | path | history}` reloads a thread by id after any process death (state DB first, filesystem fallback); `thread/fork {threadId, lastTurnId | beforeTurnId, ephemeral}` branches; `thread/read {threadId, includeTurns}` reads without loading and reports runtime `status` (`notLoaded | idle | systemError | active{activeFlags: waitingOnApproval | waitingOnUserInput}`); `thread/list` (note: `sourceKinds` defaults to `cli` and `vscode`, so pass `["appServer"]` to see harness threads), `thread/archive`, `thread/unarchive`, `thread/delete`, `thread/unsubscribe`, `thread/compact/start`, `thread/revert {beforeTurnId}` (history only, "does not revert local file changes", writes a new rollout id). Identifiers: thread id, `sessionId` (tree root), `forkedFromId`, turn id, item id, rollout path. Rollouts live at `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<ts>-<thread_id>.jsonl` (archived under `archived_sessions/`), first line `session_meta`, then `{timestamp, type, payload}` lines of kinds including `turn_context`, `response_item`, `event_msg`, `compacted`, `token_usage_record` (exact enum location UNVERIFIED); `ephemeral: true` threads are never written. `codex exec` adds `--json`, `--ephemeral`, `resume <id>`, `fork <id>`; there is no `--session-id` (feature request closed "not planned"). Reattach after a worker crash is native by id, but a running turn does not survive the app-server process; the harness marks `reattach` native-for-history, emulated-for-turn.

### 2. Turn control

`turn/start {threadId, input[], cwd?, model?, approvalPolicy?, sandboxPolicy? | permissions?, outputSchema?, ...}` returns `{turn:{id, status:"inProgress"}}` and emits `turn/started`; overrides become the thread's defaults. A second `turn/start` while a turn is active is neither queued nor rejected: core `TurnInputMode::StartOrSteer` steers it into the active turn, returns that turn's id and emits no `turn/started` (rejected only for review or compact turns, or an output-schema mismatch). `turn/steer {threadId, input, expectedTurnId}` is the explicit mid-turn injection; it errors when no turn is active or the id mismatches. `turn/interrupt {threadId, turnId}` responds after `TurnAborted`, then `turn/completed` with `turn.status: "interrupted"` and `serverRequest/resolved` for cleared approvals; the latest main commit makes interrupts instant by default. Real queueing is the experimental `thread/queue/*` surface (`add`, `list`, `update`, `delete`, `reorder`, `start`, `thread/queue/changed`). No pause for turns (only `thread/goal/*`). Fork is native (`thread/fork`, `thread/revert`, `codex exec fork`).

Mapping: `send_turn` native but the harness must gate on `thread/read.status` or its own turn ledger so an admitted follow-up is `wait_then_send` rather than an accidental steer; `interrupt_and_inject` native as `cooperative_inject` (`turn/steer`) and as `cancel_and_replace` (`turn/interrupt` then `turn/start`); `pause` emulated (interrupt at a boundary, or `pause_at_tool_gate` by withholding an approval response while the thread reports `waitingOnApproval`); `fork` native for conversation, emulated for workspace.

### 3. Hooks and middleware

In-band interception is the set of server-to-client requests: `item/commandExecution/requestApproval` (decisions `accept`, `acceptForSession`, `decline`, `cancel`, `acceptWithExecpolicyAmendment`, `applyNetworkPolicyAmendment`; `decline` denies and continues, `cancel` denies and interrupts), `item/fileChange/requestApproval`, `item/permissions/requestApproval`, `item/tool/requestUserInput`, `mcpServer/elicitation/request`, `item/tool/call` (client-executed dynamic tools declared in `thread/start.dynamicTools`, experimental, persisted in the rollout), plus `account/chatgptAuthTokens/refresh`. Approval policy wire values are kebab-case `untrusted`, `on-request`, `never`, `granular{...}` (docs examples show camelCase `onRequest`; verify against the generated schema); sandbox `read-only`, `workspace-write`, `danger-full-access` or `sandboxPolicy` objects or a named `permissions` profile; `approvalsReviewer: user | auto_review`. Under `never` the agent runs inside the sandbox without asking, so a custom decider blocks side effects only when the policy prompts; built-in server-side tools (web search, image view) are not individually interceptable over JSON-RPC. Lifecycle hooks (`features.hooks`, default on): `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PreCompact`, `PostCompact`, `SubagentStart`, `SubagentStop`, `Stop`, `Interrupt`; handlers `command` and `mcp_tool` from `~/.codex/hooks.json`, `[hooks]` in `config.toml`, `<repo>/.codex/hooks.json` (trusted projects), plugins or managed `requirements.toml`; `PreToolUse` returns `permissionDecision allow | deny` and `updatedInput`; exit code 2 blocks; hook runs surface as `hook/started` and `hook/completed`. The `notify` config runs a program on `agent-turn-complete`. Per-thread injection: `model`, `cwd`, `sandbox`, `approvalPolicy`, `baseInstructions`, `developerInstructions`, `dynamicTools`, `config` (a map of `config.toml` overrides), `ephemeral`; MCP servers only through config (`mcp_servers.<id>`, `config/mcpServer/reload`); skills as input items `{type:"skill", name, path}`. Nothing runs in-process: the Python SDK's `approval_handler(method, params) -> dict` is the only callback and it answers the JSON-RPC requests above (default `{"decision":"accept"}`).

### 4. Transcript as the source of truth

Notifications: `thread/started`, `thread/status/changed`, `thread/tokenUsage/updated {threadId, turnId, tokenUsage{total, last, modelContextWindow}}` with `TokenUsage{input_tokens, cached_input_tokens, cache_write_input_tokens, output_tokens, reasoning_output_tokens, total_tokens}`, `turn/started`, `turn/completed {turn.status: completed | interrupted | failed, error?}`, `turn/diff/updated`, `turn/plan/updated`, `item/started`, `item/completed` (documented as "the authoritative state"), deltas `item/agentMessage/delta`, `item/reasoning/*`, `item/commandExecution/outputDelta`, `item/fileChange/patchUpdated`, `item/mcpToolCall/progress`, `serverRequest/resolved`, `hook/*`, `account/rateLimits/updated`, `model/rerouted`, `error`. Item types: `userMessage`, `agentMessage`, `reasoning`, `commandExecution{command, cwd, status, exitCode?, durationMs?}`, `fileChange{changes[{path, kind, diff}], status}`, `mcpToolCall`, `dynamicToolCall`, `webSearch`, `imageView`, `subAgentActivity`, `contextCompaction`, review markers; statuses `inProgress | completed | failed | declined`. Every item id is stable across start, deltas and completion; turn ids and thread ids are stable. `codex exec --json` emits the snake_case equivalents (`thread.started`, `turn.started`, `item.*`, `turn.completed{usage}`, `turn.failed`).

Verdict: the richest deterministic substrate of the three: thread, turn and item identity are explicit, per-turn usage is `tokenUsage.last`, and approvals are request/response pairs with ids. Missing: no cost on the wire (`ThreadUsage` with USD micros exists in source but no documented method returns it; per-turn USD goes only to OTel); deltas carry `itemId` but no sequence number, so ordering is the connection order; no documented guarantee that a late-joining connection receives a running turn's earlier events (UNVERIFIED).

### 5. Inspection

Live on the same connection after `thread/start` or `thread/resume`; partial text, reasoning summaries, command output and diffs stream as deltas; `thread/status/changed.activeFlags` exposes blocked-on-approval. A second connection over `ws://` or `unix://` can `thread/resume` a loaded thread (attachment operations are serialized across connections); fan-out of an in-flight turn is implied, not stated. After the fact: `thread/read {includeTurns:true}`, `thread/turns/list`, `thread/items/list`, or the rollout file.

### 6. Placement

Worker-hosted: the app-server is a local process; Python `openai-codex` launches `<codex_bin> app-server --listen stdio://` with `experimentalApi: true` and client name `codex_python_sdk`. Auth: `codex login` (ChatGPT OAuth or device code), `codex login --with-api-key`, `CODEX_API_KEY` / `OPENAI_API_KEY`; credentials in `$CODEX_HOME/auth.json` or the OS keyring; `account/*` methods over the protocol. Cloud: Codex cloud tasks run from ChatGPT or `codex cloud exec | list | status | apply | diff`; no public REST API is documented (UNVERIFIED) and the app-server protocol does not drive cloud tasks (only `thread/resume.history` for importing cloud history). A Codex cloud profile would therefore be `start` and `observe`-by-polling only, with `cancel_turn` unsupported.

### 7. Pins

`@openai/codex` 0.161.0 (npm, modified 2026-10-07T16:16 UTC; GitHub release `rust-v0.161.0` 2026-10-07T15:58 UTC); `@openai/codex-sdk` 0.161.0 (TypeScript, wraps `codex exec --experimental-json`, no steer, interrupt or approval callbacks); `openai-codex` 0.161.0 (official Python SDK, PyPI 2026-10-07, `requires_python >=3.10`, needs CLI >= 0.151.0 for `ExternalMessage` and `include_turns`; the PyPI names `openai-codex-sdk` and `codex-sdk` are third parties). Protocol: no separate version number; the schema under `codex-rs/app-server-protocol/schema/json/` (v2, `codex_app_server_protocol.v2.schemas.json`) is regenerated per release; repo `main` read at commit `406b0c44460cf71e90c21c7abe6e581add3a6421` (2026-10-07). Docs at learn.chatgpt.com carry no dates.

## Cursor via the Python SDK and the Cloud Agents API

### 1. Lifecycle

`cursor_sdk` is a client for a bundled `cursor-sdk-bridge` binary (Connect/protobuf over loopback, protocol `sdk.v1`) that embeds `@cursor/sdk`; sync `Agent`, `Run`, `CursorClient` and async `AsyncAgent`, `AsyncRun`, `AsyncCursorClient`. `Agent.create(model=, local=LocalAgentOptions(...) | cloud=CloudAgentOptions(...))` returns `agent_id` immediately (`agent-<uuid>` local, `bc-<uuid>` cloud); `agent.send(message, options, idempotency_key=) -> Run`; `Agent.resume(agent_id)` reloads by id (runtime inferred from the prefix; inline `mcp_servers`, `tools`, `disallowed_tools`, `custom_tools` are not persisted across resume); `Agent.get_run(run_id)`, `client.agents.list(runtime=, cwd=)`, `list_runs`, `archive` (idempotent soft delete), `unarchive`, `delete`. Local agents persist through the bridge's per-workspace state root (default `~/.cursor/sdk-agent-store/<hash>`, `CURSOR_SDK_BRIDGE_STATE_ROOT`) with `LocalAgentStoreConfig.type` `sqlite` (default), `jsonl` or `custom`; resuming requires the same workspace. Identifiers: `agent_id`, `run.id` (`run-<uuid>` cloud), `idempotency_key` on create (cloud) and on `send`, `request_id` on errors; `Run.request_id` is documented for TypeScript only (UNVERIFIED in Python). Cloud agents and runs survive the caller disconnecting; local runs die with the Python process and `Agent.resume` continues from the last checkpoint. Reattach: native for cloud (`Agent.resume` + `Agent.get_run` then `stream()` within retention), emulated for local.

### 2. Turn control

Follow-up is `agent.send()`. Cloud rejects a send while a run is `CREATING` or `RUNNING` with `AgentBusyError` (HTTP 409 `agent_busy`, not retryable); local has no busy error and `SendOptions(local={"force": True})` expires a stuck run; concurrent local sends are undocumented. There is no queue in the SDK. `run.cancel()` is terminal (`cancelled`; in-flight tool calls stop, partial text stays; REST `409 run_not_cancellable` on a finished run). Steer: absent from the Python SDK and from the bridge proto (`SdkAgentService` has no Steer RPC); TypeScript `run.steer(text)` returns `complete_delivered | revert_to_followup` on local runs only, always `revert_to_followup` on cloud. No pause, fork or branch in Python, TypeScript, the bridge or REST v1 (v0 `POST /v0/agents/{id}/stop` is legacy). Statuses: Python `running | finished | error | cancelled | expired`; REST run `CREATING | RUNNING | FINISHED | ERROR | CANCELLED | EXPIRED`; agent `ACTIVE | IDLE | ARCHIVED`.

Mapping: `send_turn` native with `wait_then_send` semantics (the harness waits for `IDLE` or `finished`); `interrupt_and_inject` emulated as `cancel_and_replace` (`run.cancel()` then `send()`); `pause` unsupported; `fork` unsupported natively, emulated by a fresh agent hydrated from an immutable context and patch snapshot, as RUNTIME-CONTRACTS already requires.

### 3. Hooks and middleware

In-process Python callbacks are observe-only: `SendOptions.on_delta(InteractionUpdate)` and `on_step(ConversationStep)`. There is no approval callback; the `request` stream message (`SDKRequestMessage.request_id`, "awaiting user input or approval") has no documented response API. `LocalAgentOptions`: `cwd`, `dirs`, `setting_sources` (`project | user | team | mdm | plugins | all`), `sandbox_options` (bubblewrap or seatbelt, writes limited to cwd, temp and a `sandbox.json` allowlist, network denied by default), `store`, `auto_review` (IDE classifier, best effort), `custom_tools` (`CustomTool(execute, description, input_schema, output_schema)`, exposed as an MCP server, local only). `AgentOptions`: `tools` and `disallowed_tools` (local only), `agents` (subagents), `mcp_servers`, `mode` (`agent | plan`). No `system_prompt` in Python (TypeScript `systemPrompt` is local-only and per-account). Skills and rules load only from workspace folders. Blocking is file-based: `.cursor/hooks.json` in `cwd` or `~/.cursor/hooks.json`, events `sessionStart`, `sessionEnd`, `preToolUse` (`permission: allow | deny`, `updated_input`; `ask` accepted but not enforced), `postToolUse`, `postToolUseFailure`, `subagentStart`, `subagentStop`, `beforeShellExecution` / `afterShellExecution` (`allow | deny | ask`), `beforeMCPExecution` / `afterMCPExecution`, `beforeReadFile`, `afterFileEdit`, `beforeSubmitPrompt`, `preCompact` (observe only), `stop`, `afterAgentResponse`, `afterAgentThought`; exit code 2 denies; deny beats ask beats allow. Cloud agents run command hooks only, from project and team sources, without `sessionStart`, `sessionEnd` or MCP hooks. What `ask` does in a headless run is UNVERIFIED (the TypeScript sandbox doc says there is no human-in-the-loop flow in headless runs). Hooks are spawned processes, so a Mission Control side-effect gate must be a command hook that calls back to the worker, not a Python function.

### 4. Transcript as the source of truth

Python `SDKMessage` union: `system` (`init`: model, tools), `user`, `assistant` (`TextBlock | ToolUseBlock`), `thinking`, `tool_call {call_id, name, status running | completed | error, args?, result?, truncated?}`, `status`, `task`, `request {request_id}`, `usage {TokenUsage}` once per turn. `call_id` is stable across the running and completed pair; `args` and `result` are declared unstable. `InteractionUpdate` deltas: text, thinking, tool-call started / completed / partial, token, step started / completed, `TurnEndedUpdate` (per-turn usage), user message appended, summary started / completed, shell output; the 1.0.32 `tool-requests-listed` update is in the changelog but not in the type list (would arrive as `UnknownInteractionUpdate`, UNVERIFIED). No `result` message in Python; terminal data is on `Run` / `RunResult` (`status`, `result`, `error`, `usage`, `git`, `duration_ms`, `model`) and `run.events()` yields `RunStreamEvent` envelopes with `kind` and `offset`. Cost: `agent.get_usage(run_id=) -> AgentUsage(usage, runs[RunUsage(run_id, usage, cost)], cost: UsageCost(raw_cost_cents, charged_cents))`, cost `None` until settled, gated per account (403 `feature_unavailable`); REST `GET /v1/agents/{id}/usage` returns tokens only. History: `run.conversation()`, `agent.list_messages()` (each with `uuid`), `run.observe(after_offset=)` replays durable events from the bridge store then follows live.

Verdict: deterministic derivation is possible from `tool_call` and `TurnEndedUpdate` events keyed on `agent_id`, `run_id`, `call_id` and the bridge offset, but the envelope is weaker than the other two: no turn id (one run can hold several turns), no item ids for messages, tool `args` / `result` schemas unstable, and billed cost arrives after the run. Mission Control must treat `UsageReport.cost` as `estimated` until `get_usage` settles.

### 5. Inspection

Live: `run.stream()` (alias `messages()`, consumable once), `run.events()`, `run.iter_text()`, `on_delta` / `on_step`, `run.on_did_change_status(cb)`; partial text and in-flight tool calls (`status: running` with args) are observable. Resumable replay: `run.observe(after_offset)` (only `ObserveRun` offsets are durable; `Send` offsets may interleave non-durable events). Cloud REST: `GET /v1/agents/{id}/runs/{runId}/stream` SSE (`status`, `assistant`, `thinking`, `tool_call`, `interaction_update`, `heartbeat`, `result`, `error`, `done`), `Last-Event-ID` resume within `X-Cursor-Stream-Retention-Seconds` (value unpublished), `410 stream_expired` then `GET .../runs/{runId}`; v1 webhooks are still "coming soon" (v0 `statusChange` on `FINISHED` / `ERROR` only); no v1 conversation endpoint (v0 only).

### 6. Placement

Local: agent loop in the bridge subprocess on the worker, inference always Cursor-hosted; cloud: one VM per agent (Cursor-managed, or self-hosted `pool` / `machine`). Auth: `CURSOR_API_KEY` or `api_key` (user or service-account keys; Team Admin keys unsupported; no `Cursor.auth.login()` in Python); `POST /v1/sub-tokens` mints one-hour user-scoped worker tokens (REST only). Local-only: `custom_tools`, `tools`, `store`, `sandbox_options`, `auto_review`, `setting_sources`, background-subagent follow-up turns. Cloud-only: artifacts, `env_vars`, `metadata`, auto-PR and branch options, `AgentBusyError`, create-time `idempotency_key`. Rate limits: REST "standard" (default 20 requests per minute per endpoint); concurrent cloud agents per account undocumented.

### 7. Pins

`cursor-sdk` 1.0.37 (PyPI, uploaded 2026-10-07T20:05 UTC, `Requires-Python >=3.10`, `httpx>=0.27,<1`); the surface above was read against the docs current for 1.0.36 (PyPI 2026-10-05, `@cursor/sdk` 1.0.36, `sdk-bridge` v1.0.36 with `proto/manifest.json` `sdkVersion 1.0.36`, protocol `sdk.v1`); the release-notes page's latest entry is 1.0.35 (Sep 30, 2026), so 1.0.36 and 1.0.37 contents are UNVERIFIED. Cloud Agents API v1 is "Public beta" (`https://cursor.com/docs-static/cloud-agents-openapi.yaml`); v0 is legacy. The hooks page is undated.

## Deterministic state accumulation

The [Reducer](../../GLOSSARY.md) must derive attempt lifecycle, phase and settlement from provider events alone; the agent never writes mission state. Proposal, per ADR-0007 and workflow 09's Native Event Store:

- **Persist** every provider frame the worker observes, verbatim and before any derivation, keyed by `(harness_execution_id, generation, provider_dedupe_key)`. Dedupe keys: Claude `message.uuid` (fall back to `(session_id, message_id, block index)` for assistant blocks); Codex `(threadId, turnId, itemId, method)` with a worker-assigned arrival ordinal for deltas; Cursor the bridge `event.offset` for local runs and the SSE `id` for cloud. Partial deltas are persisted but the reducer reads only closing facts: Claude `AssistantMessage` blocks, `UserMessage.tool_use_result` and `ResultMessage`; Codex `item/completed` and `turn/completed`; Cursor `tool_call{status: completed | error}`, `TurnEndedUpdate` and the terminal `RunResult`.
- **Runtime Unit identity**: Claude `(session_id, turn ordinal from ResultMessage.uuid)`, with `parent_tool_use_id` naming subordinates; Codex `(thread id, turn id)` with item ids as effect candidates and `sessionId` as lineage root; Cursor `(agent_id, run_id)` with `call_id` for tool effects and no native turn id (derive turn ordinals from `usage` / `TurnEndedUpdate` counts).
- **Derived facts**: phase (`executing`, `awaiting_human` from Claude `requires_action` or `can_use_tool` pending, Codex `waitingOnApproval | waitingOnUserInput`, Cursor `request`), tool effects (stable tool-call ids on all three; Codex and Claude also give exit codes and diffs), usage (settled tokens per turn on all three; cost `estimated` on Claude, `unknown` on Codex, `estimated` then `settled` on Cursor), terminal execution result (Claude `subtype` + `terminal_reason`; Codex `turn.status`; Cursor `RunResult.status`) which becomes an attempt result and completion candidate, never acceptance.
- **Generation fencing** attaches to the harness execution handle at launch: Claude to the subprocess instance (a resumed session in a new process is a new generation; frames from an older process are rejected by `session_state_changed` ordering and the launch-time `init.uuid`); Codex to the app-server connection plus `turnId` (a `turn/start` answered with a steered id is logged as a delivery report `cooperative_inject`, not a new turn); Cursor to `run_id` (every send after a cancel is a new generation; a stale `tool_call` from a cancelled run carries the old `run_id`).
- **Effect claims** stay in the ledger: a `PreToolUse` / `can_use_tool` (Claude), an approval response (Codex) or a `beforeShellExecution` command hook (Cursor) must consult the [Stop Fence](../../GLOSSARY.md) before allowing a side effect, and must write the [Operation Intent](../../GLOSSARY.md) keyed on the tool-call id before returning allow.

## Open questions

1. Claude: does the Python `interrupt()` parse the `interrupt_receipt_v1` response, and can the raw `cancel_queued` control request be sent through the Python transport? Is `queued_turn_count` present on Python `ResultMessage` (it is absent from the dataclass read)?
2. Claude cloud: is there any programmatic observe, cancel or usage surface for cloud sessions beyond `claude -p --cloud <id>`? Without one the cloud profile cannot satisfy `observe`.
3. Codex: does a second ws/unix connection receive an in-flight turn's earlier notifications on `thread/resume`? What is the exact `RolloutItem` enum and is the rollout format stable enough to be a recovery source, or must the worker's persisted frames be the only record?
4. Codex: approval policy casing (`on-request` in source vs `onRequest` in docs) must be checked against the generated schema of the pinned release before the adapter is written; app-server is labelled experimental, so a qualification gate must say which release is pinned.
5. Cursor: behavior of `preToolUse` / `beforeShellExecution` returning `ask` in a headless Python run; Python exposure of `Run.request_id`; concurrent local `send()`; the 1.0.36 and 1.0.37 changes (no release notes).
6. All three: none exposes a native pause; ADR-0018's "emulated pause" is `pause_at_tool_gate` on Claude and Codex and unsupported on Cursor, which affects the Cursor lane's `describe` honesty requirement.
7. Whether the Deep Agents-style `Materialization` can record intended versus actual versions for a bundled CLI (Claude 2.1.292 inside the wheel) and a bridge binary (Cursor) the way it does for pinned Python packages.
