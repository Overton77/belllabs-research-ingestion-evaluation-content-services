## Canonical identity grammar

- BellLabs run: `(request_scope, belllabs_run_id)`
- Execution epoch: `(request_scope, belllabs_run_id, execution_epoch)`
- Graph deployment: provider-qualified graph and deployment endpoint identities
- Agent thread/run: BellLabs epoch plus Agent Server thread/run identifiers
- LangGraph checkpoint: qualified by request, BellLabs run, epoch, thread, namespace, and
  checkpoint ID
- Semantic attempt: immutable operation binding plus semantic attempt identity
- Transport attempt: provider-qualified retry identity, never semantic authority
- Child thread/run: exactly one qualified parent; parent and child BellLabs runs differ

Runtime-supplied identifiers are admitted only after matching the frozen binding, deployment,
submission, and request scope.

New operation binding, settlement, and technical-attempt IDs include request scope in their
identity material, and persistence uniqueness is scoped by request scope.

## Authority and storage map

- PostgreSQL remains authoritative for run control, runtime execution bindings, transport
  attempts, interventions, interrupts, async task projections, effect claims, journal
  mutations, technical attempts, settlements, lifecycle transitions, budget ledger writes,
  and outbox events.
- MongoDB remains authoritative for immutable published definitions and semantic
  `OperationExecutionBinding` records.
- The active artifact-acceptance executor freezes its immutable binding in Mongo, acquires the
  consequential claim in PostgreSQL before invoking the provider, stages the exact result
  replay manifest outside the transaction, then commits settlement, command result, run
  projection, budget, lifecycle, ledger, and outbox together through the PostgreSQL journal.
  The replay manifest contains governed metadata and output references only; raw output text,
  structured output, and runtime event payloads are not persisted there.
- Mongo v2 binding authority uses exact canonical digests, source lineage, scoped reads/writes,
  dual-read fallback, idempotent backfill, and quarantine. The live semantic binding services
  now use `operation_binding_write_authority` and
  `operation_binding_legacy_read_fallback`; the selector is no longer dormant.
- LangGraph checkpoints, Store, Agent Server, and Temporal are execution substrates and
  projections, not BellLabs domain authority.

## Migration and rollback

Forward migration: `0012_graph_runtime_operation_journal.sql`.

It creates runtime coordination and operation journal tables, scoped uniqueness constraints,
composite foreign keys, reconciliation/lease indexes, RLS policies, and least-privilege grants.
The Agent Runtime role may read runtime records and update only heartbeat/lease columns.
Operations receives read-only access.

The Mongo migration is non-destructive:

1. Keep legacy records immutable.
2. Backfill v2 records in binding-ID cursor order.
3. Verify valid source count, canonical digest, identity, scope, and source lineage.
4. Quarantine malformed/conflicting source records.
5. Switch the configured write authority to v2.
6. During the accepted rollback window, route reads/writes back to legacy authority without
   deleting v2 or legacy records.

## Atomic operation state machine

1. Validate the complete mutation and deny shadow claims.
2. Set transaction-local request scope and acquire the scoped advisory lock.
3. Lock the BellLabs run version.
4. insert or exactly validate the immutable effect claim.
5. Insert the full-intent journal mutation ID/digest, or accept only an identical replay.
6. Insert or exactly validate attempt and settlement records.
7. Apply run, budget, lifecycle, ledger, and outbox changes in the same transaction.
8. Commit once; any injected failure rolls back every write.

Ambiguous provider acceptance remains `reconciliation_required`; the system does not claim
exactly-once execution.

## Runtime-neutral ports

- `GraphRuntimeClient` handles submit/inspect/intervene behavior behind exact runtime selection.
- `RuntimeNeutralOperationDispatcher` executes the same frozen operation invocation through a
  legacy or graph adapter and rejects adapter mutation of semantic authority.
- `GraphRuntimeDispatchService` reserves one binding before provider dispatch and reconciles
  ambiguous acceptance.
- `RuntimeInterventionService` rechecks run/checkpoint authority and requires a matching,
  explicit privileged-repair approval.
- `RuntimeReconciliationService` admits observed provider facts only when binding, submission,
  deployment, and qualified runtime identities match.

## Capability and compatibility position

- Stable contract-only features are enabled through exact compiled definitions.
- Beta/preview runtime features remain represented in capability maturity records and require
  an explicit fallback; they are not implicitly enabled.
- Existing ERCs remain BellLabs authority. `RunPlan` records their exact digest rather than
  replacing them.
- Published definition references remain content-addressed and versioned.
- Provider fields are additive projections in v2 APIs; they do not alter existing semantic
  operation identity.
- Future checkpoints must preserve the qualified identity grammar and declared checkpoint
  compatibility key.
