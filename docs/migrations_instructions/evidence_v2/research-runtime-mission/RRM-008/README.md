## Implemented contracts and seams

**The saga, end to end (REQ-CP-EXEC-008 steps 1–7).**

1. **Journal first.** `CancelAction` on run control records the `cancel` boundary command (`accepted`, by `run_control`) in the `cancel` sequence space before anything is sent (`app/domain/run_control/reducer.py`, unchanged for this step). `pending_delivery` now includes `cancel` commands (`app/application/run_control/run_control_repository.py`); `deliver_pending` delivers the `cancel` space first and halts each space independently on a transport failure (`app/application/run_control/boundary_interventions.py`).
2. **Deliver root-first through the ledger.** `TemporalBoundaryCommandTransport._deliver_cancel` (`app/integrations/temporal_boundary_commands.py`) sends the dedicated Update `deliver_cancel(CancelDelivery) -> CancelAck` to the root (`BellLabsRunWorkflow`, patch `rrm-008-governed-root-cancel`), then to the family; only the family acknowledgement records `delivered` (by `boundary-delivery`, `transport_ref = <family>@segment:<n>`). `stale_generation` / `stale_target` acknowledgements are terminal rejections. The cancel never consumes an `execution` sequence, so the families' contiguity checks are untouched (RRM-007 N1). Under the patch the raw `request_cancel` signal is a hint only (legacy channel kept for pre-patch histories).
3. **Reach running cognition.** `OperationWorkflow` (`app/temporal/workflows/operation.py`, patch `rrm-008-operation-cancellation-saga`) starts `operation.execute` with `heartbeat_timeout` and `ActivityCancellationType.TRY_CANCEL`; the Activity heartbeats compact progress (`app/application/operations/operation_progress.py`, payload `belllabs.cognition-heartbeat.v1`: unit key, generation, attempt, phase, latest checkpoint keys) every third of its heartbeat timeout (`app/temporal/operation_activities.py`), so the cancel arrives as `asyncio.CancelledError` inside the Deep Agent step. `OperationExecutionService._dispatch_and_settle` catches it (unless the lease deadline expired) and settles the unit `cancelled` with its latest durable checkpoint as the result checkpoint (`app/application/operations/operation_execution.py`; `DeepAgentsRuntime.observe_latest` captures the leaf with `allow_pending=True` and the usage of completed calls, `app/integrations/agents/deep_agents/adapter.py`). The workflow then runs the new `operation.cancel` Activity (unlimited retries within `schedule_to_close = 2*timeout + heartbeat`) until the settlement is visible or the lease expires; a second holder takes a lost cancelling holder's lease over and settles exactly the recorded manifest.
4. **Children.** `AsyncSubagentService.cancel_children` (`app/application/async_subagents/service.py`) cancels every active child of the parent binding (journaled intent, provider request, acknowledgement or ambiguity recorded), rejects a blocking child without a result decision, settles it against the parent budget, and leaves unattributed usage `pending_usage` on the child's effect. New in `64585a5`: the parent's result decision is also recorded in run control against the child's terminal lifecycle fact (`RunControlAsyncChildEffects.decide_result`, `app/application/async_subagents/parent_effects.py`; port method `AsyncSubagentParentEffectsPort.decide_result`). Without it a run with a required/degradable child could never terminalize (`unresolved_async_children`); the RRM-013 flows never terminalized a parent run, so this was latent until the live proof.
5. **Reconcile usage, reservations, effects.** The cancelled settlement releases the unit reservation, settles the unit effect `cancelled`, records the usage of completed calls (an in-flight call is unobservable and recorded by nothing). An unsettled consequential tool effect at the moment of cancel parks the unit `in_doubt unsettled_effect_claims` with a governed incident instead of being settled over (ambiguous effects never become speculative reexecution). A child's pending usage blocks the run's terminalization until a privileged `reconcile_usage`; the families wait on the `liability_reconciled` hint signal or a doubling timer (30 s to 3600 s).
6. **Terminal cancellation is immutable.** The families propose `cancelled` terminalization (`StageGraphCompletionProposal.cancelled`, `GoalDirectedRunResult.status == "cancelled"` with `convergence_proposal None`); run control records `applied` on the `cancel` command when the terminal outcome is `cancelled`. Late or superseded outputs are rejected `run_is_terminal`; a late admission of a child result raises (`late or superseded child result cannot mutate the parent`).
7. **Families.** StageGraph (`app/temporal/workflows/stagegraph.py`, patch `rrm-008-stagegraph-cancellation-saga`) cancels each active child workflow once, rejects pending commands `superseded`, skips pause holds while cancelling, carries `cancel_requested` across Continue-As-New, and waits on liability rejections. GoalDirected (`app/temporal/workflows/goal_directed.py`, patch `rrm-008-goal-cancellation-saga`) replaces the `goal_cancelling` failure with `_cancellation_saga`: the cancelled/failed/completed settlement of the active unit is consumed through `reconcile_operation` (`operation_disposition`), pending commands are rejected `superseded`, the baseline is released (`goal:usage:baseline`, `:at-version:{v}` on a stale retry, built on RRM-016's `_enter_cancellation`), and `_terminalize_cancelled` loops with a digest probe and liability waits. `StageGraphDecisionService.initialize` retries a stale `start` once at the reported version so a cancel accepted before the family starts still binds the execution target and terminalizes through the saga.

**Timeout meanings (REQ-CP-EXEC-008 step 3, ticket item 2).**

| Setting | Where | Meaning |
|---|---|---|
| `OperationWorkflowRequest.timeout_seconds` → `start_to_close_timeout` of `operation.execute` | `app/temporal/workflows/operation.py` | Maximum time one holder may run the unit; the application lease deadline (`_LEASE_DEADLINE`) is derived from the Activity's `started_time + start_to_close_timeout`. Expiry is `OperationLeaseExpired`, not a cancel. |
| `OperationWorkflowRequest.heartbeat_timeout_seconds` (default 30, 1–3600) → `heartbeat_timeout` of `operation.execute` and `operation.cancel` | same | Worker-loss detection and cancel delivery: a worker that stops heartbeating is detected after this long; a cancel is delivered on the next heartbeat response. |
| Heartbeat interval = `heartbeat_timeout / 3`, at least 1 s (default 15 s when no timeout is declared) | `app/temporal/operation_activities.py` (`heartbeat_interval`, `HEARTBEAT_FRACTION`) | How often progress is reported. A cancel is delivered on the next heartbeat the SDK actually sends. The worker throttles heartbeats to at most one per `0.8 * heartbeat_timeout` (24 s at the default 30 s), so the delivery latency is bounded by that throttle, not by one interval (re-review fixture fix). |
| `operation.execute` retries: `RetryPolicy(maximum_attempts=3)` | same | Unchanged from RRM-004: each attempt reclassifies the unit from its lineage. |
| `operation.cancel`: `start_to_close = timeout_seconds`, `schedule_to_close = 2*timeout_seconds + heartbeat_timeout_seconds`, retries unlimited (`maximum_attempts=0`), `TRY_CANCEL` shielded against a repeated workflow cancel | same | Reconciliation after a cancel is retried until the live holder's settlement is visible (`operation_execution_in_progress`) or its lease expires; it can never be cut short by a second cancel. |
| Family liability backoff: `cancellation_retry_seconds` (default 30) doubling to 3600 s, or the `liability_reconciled` signal | `app/temporal/workflows/{stagegraph,goal_directed}.py` | How long a family waits between terminalization retries while a liability (pending usage, unsettled effect, unresolved child, operator wait) remains. |

**Decision, RRM-004 finding 4 (shared GoalDirected session namespace).** The head advances over the settled branch by a recorded transition to the unit's latest durable checkpoint; no session rollover. This holds for all four cases: cancellation of an `interrupted` unit (transition `interrupted`, settlement `cancelled`), a provider `failed` settlement over a partial stamped lineage (transition `interrupted`, settlement `failed/runtime_failed`), a budget violation after a terminal leaf (transition `terminal_unobserved`, settlement `failed/budget_exceeded`), and `abandon_unit` under cancel (settlement `cancelled/in_doubt_abandoned`, namespace released). The next unit in the same session classifies `not_submitted` with that head as its source and completes (`test_shared_session_head_advances_over_a_unit_settled_without_completing`, three parametrized cases). Failed settlements carry `latest_capture` so the head advances even when the runtime raised (`RuntimeInvocationFailure.latest_capture`).

**Decisions on children.** A cancelled child's unattributed usage stays pending and keeps the run `cancelling` until a privileged `reconcile_usage` records what the provider attributes (zero is a recorded decision, not a default). A blocking child is rejected before settlement so its late result can never mutate the cancelled parent. An orphan is a cancelled observation. Linked-run authority is untouched (the child's own run is governed by its own authority; only the parent's link, effect and usage are reconciled).

#### Fixture fix (`4f8543b`, re-review verdict `approve_with_fixes`)

**Cause.** Since RRM-008 every `OperationWorkflow` reconciles a cancelled unit through `operation.cancel`, and a cancel reaches a running `operation.execute` only through its heartbeat (`TRY_CANCEL`). `FakeStageGraphActivities` (WP-BP-010) registered no `operation.cancel`, and its fake `execute` never heartbeated. The slow-sibling test cancels one sibling, so its `operation.cancel` failed as unregistered and retried without limit until its schedule-to-close (`2 * 120 + 30` s) expired: about 256 s.

**Fix.**
- **Shared helpers.** `tests/fixtures/operation_activities.py` holds `wait_heartbeating`, `sleep_heartbeating`, `cancelled_operation_result` (the boundary's `cancelled` result for the exact binding) and `RecordingOperationCancel`.
- **Every worker set serving `operation.execute` now also serves `operation.cancel`** (found by grep):
  - The real `OperationExecutionActivities.cancel` wherever the real `execute` is served: the RRM-004 restart worker and drill, RRM-005 inspection, RRM-006 forks (two workers), and three workers in `test_operation_execution.py` plus one in `test_checkpoint_recovery_classification.py`.
  - The real service's `cancel` in the BP-020 live test.
  - A recording fake in the BP-010 and CP-040 live tests, in the sandbox rollover test, and in the blocking signal-with-start fake.
  - The fixture settlement in `FakeStageGraphActivities`. The RRM-007 and RRM-008 StageGraph harnesses inherit it; the RRM-008 harness overrides it and no longer lists it twice.
  - `test_generic_artifact_workflow.py` runs `GenericArtifactWorkflow`, which never schedules `operation.cancel`, so nothing was added there.
- **Fake `execute` heartbeats while it waits** in the WP-BP-010, WP-BP-020, RRM-007 and RRM-008 harnesses. Tests that cancel a running fake unit set a 5 s operation heartbeat timeout: the slow-sibling test and the RRM-008 StageGraph and GoalDirected harnesses. The cancel is then delivered on the next heartbeat under time skipping.
- **Assertions are as strong as before or stronger.** The slow-sibling test now waits for the cancel to reach the running Activity while the worker is still up (before, worker shutdown could have set the flag). It also checks that exactly the slow unit ran `operation.cancel`. The sandbox rollover test checks that nothing was cancelled.

**The other slow tests.**
- **GoalDirected in-doubt saga test:** same cause, since its fake executor never heartbeated. 35 s → 4.4 s.
- **GoalDirected executor-cognition test** (about 31 s): a related cause, but no fixture is missing. It runs the real `OperationExecutionActivities` with the production default 30 s heartbeat timeout, which the real GoalDirected preparer does not override. The Activity heartbeats every 10 s, but the SDK throttles sends to one per 24 s, so the cancel arrives up to 24 s late. - **Production note for RRM-009:** it should set `heartbeat_timeout_seconds` per operation class, or a worker heartbeat throttle, to the cancel latency it wants. This is already a composition item (Unresolved risks, item 1). The timeout table above is corrected.
