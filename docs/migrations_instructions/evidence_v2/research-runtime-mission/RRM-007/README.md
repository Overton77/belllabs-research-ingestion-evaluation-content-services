## Implemented contracts and seams

**Receipt design (`CON-CP-WORKFLOW-MESSAGE-V1`).** Every boundary command (`pause`, `resume`, `satisfy_wait`, `cancel`, `reconcile_unit`) is recorded by run control as an immutable `BoundaryCommandRecord` (`belllabs.boundary-command.v1`: the exact action, its order-stable fingerprint via `contract_fingerprint`, the target boundary, the accepted run version, epoch, generation and a monotonic `target_sequence` per sequence space) plus one `BoundaryCommandReceipt` (`belllabs.boundary-receipt.v1`) per transition. The closed state machine is enforced in the domain (`RECEIPT_TRANSITIONS`, `BoundaryCommandStatus` validator) and at every write (`append_receipt`): `accepted -> delivered -> applied`, `rejected` from `accepted` or `delivered` (or as the only receipt of a command rejected at acceptance); a state already present is a no-op, terminal states never transition, so a duplicate can never apply twice. Rejection reasons are the closed set (`stale_target`, `stale_generation`, `stale_version`, `not_applicable`, `terminal_run`, `superseded`, `unauthorized`, `insufficient_budget`); reducer codes map onto it (`rejection_reason_for`). Storage: migration 0023, two insert-only tables with forced request-scope RLS.

**Requested vs applied (REQ-CP-RUN-004).** The family declares its execution target in its `start` fact (`StartAction.execution_target`, `RunProjection.execution_target`: family, family and root workflow IDs, epoch, generation). While a target is bound, an accepted `pause`/`resume`/`satisfy_wait` is validated by a dry reduction against the exact expected version, recorded as pending (`accepted` receipt, `CommandResult.reason_code = accepted_pending_application`) and **does not transition the projection**: the phase and the scoped axes change only when the boundary's `apply_boundary_command` fact is accepted (one transition that also writes the `applied` receipt atomically). Because acceptance moves no version, a family never fails on version drift caused by pending commands. With no target bound, run control is itself the boundary and records `accepted`, `delivered` and `applied` in one commit (existing callers and tests keep today's behaviour). `cancel` keeps its acceptance transition to `cancelling` and is `applied` when the reducer records the terminal outcome (`terminalize` with outcome `cancelled` writes the receipt). `reconcile_unit` keeps its reducer transition; `delivered` is recorded after the wake-up hint is signalled and `applied` when the operation boundary consumes the decision.

**Delivery (REQ-CP-EXEC-007).** `BoundaryInterventionService` is the only public entry (the API facade uses it); it accepts through run control and, when a transport is composed, delivers what is pending. `BoundaryCommandDeliveryService.deliver_pending` delivers in `target_sequence` order and stops at the first transport failure (ordering is preserved; `redeliver` re-drives safely). `TemporalBoundaryCommandTransport` delivers root-first (`BellLabsRunWorkflow.deliver_message` Update: generation and sequence validated, root receipt cache de-duplicates, a `gap` raises) and then to the family (`deliver_boundary_command` Update, new on both families). Only the family's acknowledgement records `delivered`; `stale_generation`/`stale_target` acknowledgements are terminal rejections.

**Application at the boundary.** Both families consume delivered commands in sequence order at their boundaries through the new activity `<family>.apply_boundary_command` (`BoundaryCommandApplicationService`, registered in `coordinator_activities` and composed in `create_routed_coordinator_activities` with the orchestration identity). The activity binds the current run version itself and is idempotent by command identity. StageGraph: a pause (scopes `run`/`workflow`/`stage:<id>`) blocks future admissions in scope and leaves other stages admissible; a release marks the blueprint wait satisfied; `runnable_work_remains` is computed honestly, and a new `observe_quiescence` fact keeps the aggregate phase accurate when admissible work runs out under scoped pauses (or returns). Held waits are declared to run control (`set_wait`, kind `approval`, condition `stagegraph-wait:<wait_id>`) so they are inspectable; the raw `satisfy_wait` signal is a hint only (legacy release kept behind `workflow.patched("rrm-007-governed-waits")` for old histories). GoalDirected: a pause is applied only at an iteration boundary (no unit active) and binds a `GoalPausedState` (pause decision, command, revision, next iteration, session generation and mode, handoff ref, effect frontier, held and released reservation IDs, next-iteration reservation, run version) into the `applied` receipt's `boundary_state`; the workflow waits without failing; a resume probes the next iteration's reservation (`resume_reservation` → `insufficient_budget` rejection keeps the run paused) and continues from the same interpreter state; a policy-selected pause enters run control as a `pause` bound to the convergence decision and is applied by the boundary, replacing the non-retryable `goal_paused` failure behind `workflow.patched("rrm-007-durable-goal-pause")`.

**Continue-As-New (REQ-CP-EXEC-011).** `StageGraphRunInput` carries `satisfied_wait_ids`, `declared_wait_ids`, `active_pauses`, `pending_boundary_commands`, `applied_boundary_command_ids`, `quiescent` and `technical_segment`; `GoalDirectedRunInput` carries `pending_boundary_commands`, `applied_boundary_command_ids`, `continue_as_new_iterations`, `force_continue_as_new`, and `GoalContinuationState.paused`. Handlers quiesce (`workflow.all_handlers_finished`) before continuation.

**`reconcile_unit` governed delivery (RRM-004 review).** `POST /run-control/v1/runs/{run_id}/reconcile-unit` over `UnitReconciliationService` (composed from the pool with the optional `unit_reconciliation_nudge`/`unit_reconciliation_verifier` on `app.state`); the new `reconciliation_operator` role holds `workflow_run.read` and `workflow_run.reconcile_unit` (the plain `operator` role still does not); `/commands` refuses `reconcile_unit` (422). Receipts: `accepted` (run control), `delivered` (`unit-reconciliation`, after the hint signal, transport ref = operation workflow ID), `applied` (`operation-boundary`, when `_recover_or_dispatch` acts on the decision). The signal stays the hint transport.

**Reads.** `GET /run-control/v1/runs/{run_id}/boundary-commands` (read permission) returns the ledger; `POST .../boundary-commands/redeliver` (relay permission) re-drives delivery; `RunInspection.boundary_commands` and `UnitInspection.boundary_commands` (the unit's `reconcile_unit` commands) are served by both inspection repositories; `/schemas` exports `boundary_command_status`.

### Ordering and restart proofs

- Ordering: per-run `target_sequence` assigned under the run lock only for accepted commands (rejections never consume one, so the root sees no gap); the delivery pass is sequence-ordered and halts at the first failure; the root Update validates sequence contiguity (`gap` raises and is retried by redelivery) and generation; the family applies pending deliveries in sequence order. Proven in `test_delivery_follows_target_sequence_and_stops_at_the_first_failure` and by the root receipt caches `[1]` and `[1, 2]` in the demonstration.
- Redelivery / duplicates: `duplicate` acks, `already applied` application and already-recorded receipt states are all no-ops (unit, integration and demonstration).
- Stale target: `stale_generation` (generation 2) and `stale_target` (epoch 2) deliveries are acknowledged and recorded as terminal rejections; a foreign boundary cannot apply (`stale_target`).
- Worker restart: the GoalDirected demonstration stops the only worker while paused and resumes on a new worker identity from PostgreSQL authority and the replayed history. Continue-As-New: StageGraph satisfied wait and GoalDirected paused state proven across forced continuation (time-skipping) and the StageGraph continuation on the real server.
