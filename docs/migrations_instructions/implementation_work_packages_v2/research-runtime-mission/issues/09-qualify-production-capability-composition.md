- [ ] **Session-generation admission after a sealed head (from the RRM-008 re-review).** *(Unresolved, not contained in this composition; see the evidence, "Integration with RRM-008".)* When a GoalDirected unit settles `failed` (a provider failure over a partial lineage, or a budget violation after the terminal leaf) or `timed_out`, its transition is recorded non-seedable and the session namespace head is sealed (REQ-BP-GD-012, REQ-CP-DA-017). The unit generation that sealed the head is still admitted, so its own retry settles the recorded result (`observed_unsettled`). Any later unit of that session is refused with a non-retryable `CheckpointLineageConflict` ("sealed") before any provider work (`CheckpointLineageService._refuse_sealed_head`). The family then fails the run on the unit without a typed result. To continue, the composition must admit a new `session_generation`, fresh from the handoff. It must never branch or reuse the sealed session thread. No production path admits one today. The composition (or the operator surface it exposes) owns that admission and must qualify it.
- [ ] **Superseded generation under cancellation (from the RRM-008 re-review, residual).** *(Unresolved; both windows documented in the evidence; they close with RRM-014's re-admission or an operator `operation.cancel` path.)* RRM-008 settles a generation superseded by an accepted `start_new_generation` once the run is cancelling. `OperationExecutionService.cancel` settles the claim, reservation and effect `cancelled` (`generation_superseded`) without lineage writes. Both family sagas run `operation.cancel` once for a unit that ended `in_doubt` / `generation_superseded` while the family was cancelling (patches `rrm-008-goal-settle-superseded-generation` and `rrm-008-stagegraph-settle-superseded-generation`). Two windows stay open:
  - The family consumed the `generation_superseded` result **before** the cancel. GoalDirected's reconciliation rejects an `in_doubt` result, so the family fails. StageGraph rejects the result (`operation_in_doubt`) and continues. The later cancel then has no settler for that claim, and the run waits on its liability timer. RRM-014's re-admission closes this window in the normal path. Until then, a composition that cancels such a run must run `operation.cancel` for the superseded unit, through the operator surface or a relay.
  - The superseded generation still holds an unsettled consequential effect claim. It stays `in_doubt` for the operator, who settles the effect in run control. Nothing re-dispatches `operation.cancel` after that decision, so the composition must send the unit's settlement or run the cancel again, then send `liability_reconciled`.
  - Usage of an `in_doubt` generation that is settled this way is not attributed, as with `abandon_unit`. Its reservation is released.
