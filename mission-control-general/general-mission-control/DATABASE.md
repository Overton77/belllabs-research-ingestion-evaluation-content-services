# General Mission Control database specification

The required expansion adds [context/handoff/message/process/view/notification/memory/knowledge/evaluation records](expansion/DEPLOYMENT-AND-RELEASE.md) plus scoped authoring interview/session/event persistence from [experience contracts](expansion/EXPERIENCE-AND-STREAMS.md). They belong to the same checksummed common component in both projects. External entity and vendor runtime tables retain their owners. MC-P002/MC-F002 generate/test the combined inventory before publishing migrations; no additional editable SQL authority is introduced.

Version: canonical consolidation 3, 2026-10-02. This is the logical/physical schema contract to implement, not an applied SQL migration. It is paired with [SPECIFICATION.md](SPECIFICATION.md). Both existing Supabase projects receive the same component release; application data remains in its original project.

## Installation and migration authority

The schema name is `mission_control`. Its tables/functions/types MUST be self-contained with respect to app domains. They may use PostgreSQL/Supabase primitives but MUST NOT require `corpus`, `taxonomy`, `knowledge`, `orchestration`, a biotech graph, MongoDB, or another app's `util` helpers. External domain outputs are typed immutable references rather than foreign keys into a knowledge schema.

Ownership amendment 2026-10-03 (owner correction): the canonical common SQL source and generated Mission Control-only contract are owned by the independent `mission-control-db-contract` component at `mission-control/packages/mission-control-db-contract/`. `ai-engineer-db-contract` owns AI Engineer domain entity tables only; it is neither owner nor prerequisite of this component. The component is a separately releasable package containing ordered migrations, checksums, required extensions/minimum PostgreSQL version, generated Mission Control-only contract exports, schema manifest and compatibility tests. Its schema source is authored once. Installers in each app pin the release and its checksums; they cannot edit generated/copied SQL. The release generator and schema contract tests prove that app chains assemble the same common component.

Use `mission_control.component_release` to track this component independently of unrelated whole-project migration heads. On both projects the compatible Mission Control component version and checksum set must match the service build. Application rows/capability installations may differ. An AI Engineer curriculum migration does not change Mission Control's component identity.

Install the common component into each app database while preserving unrelated Auth, membership and domain data. The clean-break policy requires no legacy Mission Control/Mongo migration, old-engine coexistence or old-history support. Start fresh common executions. If the target schema already exists, fingerprint and reconcile its ownership before applying; no blanket reset or destruction of unrelated app records is authorized.

Fresh installation and subsequent common-release upgrade/rollback-compatibility proofs use two disposable projects/databases. Applying to the two populated Supabase projects is a separate controlled release step with preflight identity checks, backup/recovery evidence and component verification. No reset of either live app is part of this plan.

## Keys types and shared columns

UUID primary keys are generated by the common application's pinned UUIDv7 generator. Text logical keys and digests are separate fields. Foreign keys are scoped to the same installation/application/tenant, using composite unique keys where necessary. Same UUID in the other Supabase project cannot establish a relationship.

Every tenant-owned record has these base columns:

```text
installation_id uuid not null
application_id text not null
tenant_id uuid not null
<record>_id uuid not null
created_at timestamptz not null
created_by_actor_ref text not null
```

Mutable aggregates add `version bigint not null`, `updated_at timestamptz`, `last_event_seq bigint` where mission-sequenced. Immutable records do not expose update/delete mutation paths. Lifecycle state columns on mutable aggregates are projections of committed domain transitions; immutable transition/event records retain history. `digest` fields have a format check; accounting uses `bigint` integer units; timestamps are UTC instants. JSONB columns require a contract name/version and validation before admission; they are not arbitrary undocumented blobs.

Installation-level catalogs/releases do not carry `tenant_id`; tenant-specific grants reference those records with full installation/application identity. Bootstrap tables are operator-only. Catalog metadata is filtered by authorization when exposed; secret values never appear there.

## Required transaction protocols

**Request admission:** lock or insert scoped request key, compare payload digest, verify authority/version, perform domain mutation, write events/outbox/result receipt and commit. Same request/digest returns original result. Changed digest returns `IDEMPOTENCY_CONFLICT`. Authorization remains checked when reading a replayed result.

**Revision activation:** lock mission, compare expected version/base head, verify submitted compiled revision/policy, compute and store transition impact, update single scheduling head, append event/outbox and commit. Competing proposals become stale. No uncommitted agent-defined graph is released.

**Run start:** in one transaction validate installation/component pins and capability grants, lock mission/budget, record immutable run/input/binding/reservation, assign workflow identity, append `run.admitted` and start outbox. Relay starts/attaches exactly that root. Workflow start acknowledgment updates runtime refs idempotently. If the database commits and Temporal is unavailable, the run stays visibly pending and retries the same delivery identity.

**Activation release:** compare interpreter decision/input state versions, lock capacity/budget, create stable activation/attempt/fenced lease and binding, register launch intent/outbox. Duplicate scheduler decisions recover the same identities. A stale worker cannot settle outputs using an old fencing token or generation.

**External effect:** journal stable intent and reserve exposure; invoke only after commit; reconcile provider receipt/identity after ambiguous response; finalize one receipt, output registration, budget settlement and events in a transaction. Stable effect identity excludes technical activity retry number and remains valid across recovery. If a new semantic attempt proposes a changed effect it receives a new identity only after prior uncertainty is resolved.

**Completion:** verify candidate identity/generation, registered output digests, expected assessment versions, human/proof resolutions, children/effects/usage frontier and pinned contract; write immutable completion decision and corresponding aggregate/event changes atomically. The evaluator reads only authorized attributable facts. Repeating evaluation with unchanged inputs recovers the recorded decision. New assessment evidence creates a new attributable decision, never a historical overwrite.

**Cancellation:** persist command and desired stop, halt new launches, request provider/subordinate cancellation, reconcile outstanding effects/checkpoints/charges, then settle activation/run outcome. An unresolved external effect remains a visible reconciliation case; cancellation does not mean undo. Nonblocking work retains an explicit parent-owned cleanup/admission policy rather than being silently orphaned.

## Security policies

The common schema is not exposed as a client mutation surface in Supabase/PostgREST. API/MCP/worker connections use least-privilege non-owner database roles without `BYPASSRLS`. Tenant business tables have enabled/forced RLS where compatible with the chosen owner/migration roles, and transaction-local trusted context `mc.installation_id`, `mc.application_id`, `mc.tenant_id`, `mc.actor_ref`. Missing/mismatched context denies access. Context setters are used only by authenticated server transactions; agents never receive SQL credentials.

Migration/owner credentials are separate from API/worker credentials. `service_role` bypasses Supabase RLS and therefore is not the default mission business-query connection. Grants, role behavior, owner paths and RLS are independently tested. [Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security).

Every local FK preserves scope; every external reference checks issuer/audience/scope/digest at use. Catalog bootstrap/install operations use narrow operator authority. No global pooled mutable client retains one tenant's context for the next request: use transaction-local settings and reset/release connections. Role-specific grants limit API versus worker mutations even if application checks fail.

## Indexes compatibility and retention

Require indexes on all scoped FK lookups; mission owner/lifecycle/updated time; run mission/lifecycle; activation run/parent/node/lifecycle; attempts by activation/no; commands by target/lifecycle; Human Tasks by assignee/lifecycle/deadline; asset ID/version/kind/status; events by mission/seq; outbox and reconciliation due/lease; intent/effect keys; native dedupe keys; artifact digest and producer. JSON indexes are added only for documented query paths, not indiscriminately.

Component releases are additive/expand-contract while previous workers/runs remain active. New constraints/type literals require service/worker compatibility before application. Destructive cleanup waits for retirement evidence and data retention decisions. Generated Mission Control-only types and runtime contracts have a golden schema parity fixture in CI.

Mission events, revisions, receipts, decisions and canonical artifact lineage retain the configured audit history. Native observations/traces and scratch objects have separate shorter bounded retention. Event streams state their retention floor; replay below it requires resync. Artifact retention cannot delete bytes still required by an active run, checkpoint or retained evidence contract. Cleanup produces its own auditable receipts.

## Required database proofs

Install/upgrade the same component in two disposable databases with deliberately different unrelated app schemas. Verify identical common tables/functions/constraints and component checksum sets. Run both with the same common service build. Exercise duplicate starts/requests, concurrent head changes, concurrent reservations, lease recovery, context leakage, scope-crossing FKs, stale-generation settlement, human-resolution races, outbox redelivery and write-response loss. Prove no table/function references a product schema or requires one app's helper library.

Live production target identities and database credentials are operator input at installation time, never values invented or copied into this specification.

For tenant-owned records define the unique scope key `(installation_id, application_id, tenant_id, <id>)` in addition to the UUID primary key. Every tenant-local FK includes that whole key; catalog FKs include installation/application scope. Mission-owned children additionally constrain their mission/run ancestry, preventing a valid same-tenant activation from referencing another run's attempt. `application_installation` has a unique installation/application pair; `tenant` references it. Enforce exactly one active installation with a partial unique index on the active predicate. Index all referencing scoped FK columns.

Required constraint templates (specification, not an executable migration):

```sql
CHECK ((lifecycle = 'completed') = (terminal_outcome IS NOT NULL));
UNIQUE (installation_id, application_id, tenant_id, activation_id, attempt_no);
UNIQUE (installation_id, application_id, tenant_id, actor_ref, action, request_key);
UNIQUE (installation_id, application_id, tenant_id, effect_key);
UNIQUE (installation_id, application_id, tenant_id, mission_id, seq);
```

`request_receipt.request_key` is the public `request_id`; `operation_intent.effect_key` is computed from installation/app/tenant/run/activation/semantic-attempt/action ordinal and pinned input digest. Both exclude Temporal technical retry and technical segment numbers. A changed semantic payload under an existing key conflicts. The canonical effect receipt may be written once; later reconciliation evidence appends records and cannot silently replace its outcome.

Mutations execute in an `asyncpg` transaction using a registry-selected pool and trusted `set_config(..., true)` transaction-local scope. JSON contracts validate with Pydantic before insertion; SQL checks protect structural lifecycle, scope and integer constraints independently. Never rely on arbitrary JSONB to enforce FK relationships. Acquire locks in the order request receipt -> mission -> run -> activation -> budget accounts sorted by ID -> effect, and retry deadlocks/serialization failures under the same request identity. Outbox/reconciliation workers claim bounded batches with `FOR UPDATE SKIP LOCKED`, expiring leases and fencing; delivery cannot occur before commit. The transaction writer locks the mission row, allocates contiguous event sequences, inserts events/outbox, and commits aggregate changes atomically. Rollback creates no visible sequence gap.

A retry request locks the source run/activation, validates uncertainty reconciliation and policy, and records a new recovery request while preserving semantic identities. A fork transaction rechecks the sealed source checkpoint, pins only eligible immutable outputs, independently admits budget/grants, creates a new run at epoch/generation/segment one, and inserts lineage/start-outbox atomically. Native checkpoint copying happens afterward with a persisted intent and target handle. The fork start-outbox entry is held (not dispatchable) until copy/hydration and continuity validation commit success; failure leaves the new run pending/blocked and its reserved budget visible. Start relay must check this prerequisite atomically when claiming delivery. Lost copy responses reconcile by the same target identity. No active child, pending command, outstanding reservation or mutable workspace ownership is copied. Diagnostic replay creates a recovery/report record only; it cannot settle business effects.

Compatibility manifest fields are `component_version`, `ordered_migrations[{key, sha256}]`, `schema_fingerprint`, `contract_schema_digest`, `min_postgres_version`, `required_extensions`, `supported_reader_versions`, `supported_writer_versions`. Declare the qualified minimum during the first migration release, using the actual disposable targets; this specification assumes no app-specific extension/helper. Migration tests compare normalized MC-only tables, columns, constraints, indexes, functions, policies and grants, excluding project-specific identity/data. Both projects must produce the same fingerprint. The service refuses writes when its required writer compatibility is absent.

For subsequent releases of the new common component, the expand/contract sequence is: add nullable fields/tables -> deploy compatible readers -> backfill using attributable reconciliation receipts -> validate constraints -> admit new writers -> retire superseded common-component writers -> consider destructive cleanup separately. MC common releases cannot bundle domain migrations. Rollback means rolling to a declared compatible build; it never means dropping new audit data or rewriting Temporal histories. Recovery tests include process death after DB commit before dispatch, provider application before response, receipt commit before acknowledgement, and checkpoint copy before result persistence.

All transaction writers follow the stated lock order. Nested admission never acquires a second independent request receipt while holding mission/effect locks; dispatch/reconciliation use separate transactions with their own stable intent IDs. Read-only request replay does not acquire aggregate locks.

## Runtime persistence and Agent Server

Begin with a private restricted runtime schema in each application's PostgreSQL for the pinned Agent Server/LangGraph persistence, subject to adapter-supported schema configuration, connection/load and recovery qualification. These runtime tables are not part of the business `mission_control` schema and do not authorize mission transitions. Do not assume a managed server product accepts an arbitrary database or schema; the selected deployable server/adapter must prove this binding, or document a required physical persistence separation before deployment.

The runtime persistence role cannot mutate mission business tables. API/mission workers cannot rely on native checkpoint contents as an acceptance record. Server submission records retain the app/installation/tenant, subordinate ID, launch/effect identity, graph version, generation, dependency policy and native run/thread handles. `subordinate_execution` is the canonical admitted child record; vendor-native graph state remains recovery data. Persist unknown submissions for reconciliation; no missing native handle permits blind relaunch.

Runtime schema setup/versioning follows the pinned server/checkpointer tooling and is tracked separately from common SQL component checksums. Retention respects unresolved children and valid checkpoints. Both apps require Agent Server restart, lost-launch, cancellation and isolation proofs. Physical separation remains an operational option rather than a required third mission database.
